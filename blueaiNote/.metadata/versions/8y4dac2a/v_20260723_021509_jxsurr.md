# adswin_x 广告创建子 Agent —— Prompt / CLAUDE.md / SKILL.md 三层职责分析与优化方案

## Context

adswin_x 的广告创建子 Agent（`ads_agent`，类 `AdsClaudeAgent`）由 Claude Agent SDK 驱动，其"人格 + 规则 + 流程"分散在三份产物里：

- **Prompt**：`src/prompt/files/adswin_x__ads_agent__ads_claude_agent_instruction.py` （用户最初引用的 `bm_recommend__claude_agent__claude_agent_sys_prompt.py` 是另一个独立 agent——报告优化助手——用的是旧的 `list_skills`/`activate_skill` MCP 机制，与本套无关）
- **CLAUDE.md**：`src/adk_app/adswin_x/CLAUDE.md`
- **SKILL.md**：`data/claude/skills/adswin_x/skills/adswin_root_skill/SKILL.md`

近期已做过一次三层内容重分配（`56fdff2`：状态契约+工具概览迁入 Prompt、协议细节瘦身为声明+URL 红线迁入 CLAUDE.md；`70e4238`：补 3 个素材转存工具、删 Prompt 里 `upsert_preview_feishu`）。但探索发现该重构留有残留问题，且三层"该装什么"缺一套明确判据。本方案先产出**分析结论 + 优化动作清单**（以磁盘文件为落地口径，不改 DB），供 review 后再决定执行。

## Part 1 · 三层在 Claude Agent SDK 中的装配机制与作用

装配全部发生在 `src/claude_agent_base/base_agent.py`（`AdsClaudeAgent` 继承 `BaseClaudeSubAgent`），每次 session 启动构造一次 `ClaudeAgentOptions`：


| 层             | SDK 装配方式                                                                     | 注入时机                                                                         | 关键代码                                                                                                                                                                                         |
| ------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Prompt**    | `system_prompt=` 参数，全量注入                                                     | **always-on**，每 session 常驻                                                   | `build_system_prompt(session_cwd)` 只做 `.replace("{session_cwd}", …)`（`claude_agent.py:19-21`）→ `options.system_prompt`（`base_agent.py:1009,1037`）                                            |
| **CLAUDE.md** | **自动加载，非拼接**：物理复制进 cwd + SDK 读 project 记忆                                    | **always-on**，作为项目记忆常驻                                                       | `shutil.copy2(src/adk_app/adswin_x/CLAUDE.md → {session_cwd}/CLAUDE.md)`（`base_agent.py:481-484`）；`cwd=session_cwd`（1032）+ `setting_sources=["project"]`（1039，受 `settings_file` 门控）触发 CLI 读取 |
| **SKILL.md**  | `plugins=[{type:local, path:…}]` + `skills="all"`，CLI 扫描 `skills/*/SKILL.md` | **on-demand**：前期仅 `name`/`description` 可见；body 仅在调用 `Skill(skill="…")` 时进上下文 | `_plugins`（`base_agent.py:1019-1027,1040-1041`）；bootstrap 在 Prompt §"启动规程" 调 `Skill(skill="adswin_root_skill")`                                                                              |


**核心结论**：三层的本质区别是**注入时机与上下文成本**——

- Prompt 与 CLAUDE.md 是"每 session 必付费"的常驻上下文（体积越小越好，只放高频、稳定、普适的内容）；
- SKILL.md 是"按需付费"的懒加载手册（可以很大、很细、迭代频繁）。
- CLAUDE.md 的加载完全依赖"复制进 cwd + `setting_sources=['project']`"这套约定，代码从不把它拼进 system prompt。

## Part 2 · 三者关系与调用拓扑

```plaintext
ads_agent system prompt (Prompt 层, §启动规程)
      │ "首先调用 Skill(skill='adswin_root_skill')"
      ▼
 adswin_root_skill/SKILL.md  (主控制流 0.0–8.0)
      ├─ §5.0.x 命名      → Skill(skill="naming_skill")   (加载一次后复用)
      ├─ §3.0.4 AI 素材   → Skill(skill="material_generate_skill")
      └─ §7.0.x 平台创建  → Skill(skill="google_ads_create_skill" / "tiktok_ads_create_skill")
                                    │
      任何平台 mutate ────────────► agent_deploy_skills 协议 (issue→mutate→log→finish)
                                     ↑ CLAUDE.md §1 将其提为"最高优先级"

```

- **Prompt ↔ SKILL.md**：Prompt 只提供入口指针（bootstrap），把详细流程完全下放给 SKILL.md。
- **CLAUDE.md ↔ 全体**：CLAUDE.md 是横切所有 skill 的"铁律层"（协议声明、运行时环境、安全红线），它约束的是"无论走哪条流程都不能破的线"。
- **agent_deploy_skills** 不是线性步骤，而是协议覆盖层，被 root skill、两个平台 skill、CLAUDE.md §1 共同指向。

## Part 3 · 数据源不对称性（决定优化怎么落地才生效）

当前 `conf/config.yaml`：`content_store.prompt_source: db`、`skill_source: db`（dev）。


| 层         | dev 运行时权威源                                                                                        | prod 运行时权威源                         | git 跟踪                         |
| --------- | ------------------------------------------------------------------------------------------------- | ----------------------------------- | ------------------------------ |
| Prompt    | **DB** `adk_prompts`（`prompt_loader._load_from_db`，按 version DESC）                                | 磁盘 `.py`（file 模式，有 mtime 热更新）       | ✅ `.py` 受跟踪                    |
| SKILL.md  | **DB** `adk_skills`**(scope=CC)**（`_materialize_claude_skills` 物化到 `session_cwd/_claude_skills/`） | 磁盘 `data/claude/skills/adswin_x/**` | ❌ 被 `.gitignore` 的 `data/*` 排除 |
| CLAUDE.md | 磁盘（`copy2`，与 db/file 无关）                                                                          | 磁盘（`copy2`）                         | ✅ 受跟踪                          |


**这解释了两件事**：① `56fdff2` 声称对 SKILL.md 的"去重"从未进版本库（文件不受跟踪）；② dev 环境改磁盘 `.py`/`SKILL.md` 不会立即生效（dev 读 DB）。

**本方案落地口径（按用户决定）**：以**磁盘文件为权威**做优化改动 + git 留档；**不触碰 DB**。dev(DB) 的同步由用户自行处理，方案会在动作清单中把这一步显式标出，避免"改了却不生效"的误判。

## Part 4 · 内容分配判据（回答"内容应该如何分配"）

一条原则贯穿：**每层只拥有自己抽象层级的内容；同一条内容只在其"最高权威所有者"层写一次，其它层用指针引用、绝不复制**（altitude + reference-don't-duplicate）。

用四个维度判断一段内容归属哪层：


| 维度    | → Prompt        | → CLAUDE.md        | → SKILL.md   |
| ----- | --------------- | ------------------ | ------------ |
| 注入时机  | always-on       | always-on          | on-demand    |
| 内容性质  | 运行时交互/状态**契约**  | 不可破的**铁律/红线/协议声明** | 可迭代的**操作流程** |
| 受众    | 运行时 agent 的行为约束 | 编码者 + agent 的硬边界   | 执行某任务时的分步手册  |
| 体积敏感度 | 高（越短越好）         | 高（越短越好）            | 低（可长可细）      |


据此，三层的**目标职责**为：

- **Prompt**：角色定位、`{session_cwd}` 文件系统边界、启动规程（bootstrap 指针）、交互契约、状态管理契约（状态机）、可用工具概览。
- **CLAUDE.md**：`agent_deploy_skills` 协议声明（最高优先级）、Python/Shell 运行时铁律（`$ADS_PYTHON`、禁 uv、脚本落 `{session_cwd}`、Edit 前先 Read）、URL/素材安全红线。
- **SKILL.md**：0.0–8.0 完整创建控制流（元数据→路径识别→叉乘→预览→三轨校验→级联创建→自愈）；流程内联的具体工具调用与分支。

## Part 5 · 发现的问题（优化点）

**P1 · 跨层重复（SKILL.md 与 Prompt/CLAUDE.md 各存一份，违反 reference-don't-duplicate）**

- SKILL.md「状态保存与状态机」(§353-371) ≈ Prompt「状态管理契约」——整段通用状态机重复。
- SKILL.md「禁止直接输出」(§373-375) ≈ Prompt「交互契约」。
- SKILL.md「URL 传递原则」(§381-383) ≈ CLAUDE.md §3「URL 安全红线」。

**P2 · 死引用** `upsert_preview_feishu`**（agent 实际调不到）**

- 该工具**未注册进 MCP server**（`ads_agent/mcp_server.py` 无此 `name=`），`70e4238` 已从 Prompt 删除，但 **SKILL.md 仍两处把它当"必用工具"引用**：§244（步骤 6.0-⑤）、§422（必用工具清单），另 §238-242 的 ④⑤（`ad_preview` 的 `{value,enum}` 格式）也是"供 upsert_preview_feishu 读取"。函数体仍留在 `tools/feishu_write.py`（DEPRECATED 兼容层）但对 agent 不可见。

**P3 · SKILL.md 脱离 git 跟踪（治理隐患）**

- `data/*` 使 `adswin_root_skill/SKILL.md` 不受版本控制，任何磁盘改动无 diff、无 review、易在下次部署被覆盖或丢失——这是 P1/P2 长期存在的根因。

**P4 · 概念一致性（低优先级）**

- Prompt「可用工具概览」保留 `Skill`/`transfer_to_root` 属正常（`Skill` 是 CLI 内建）；无需改。仅需确保 adswin_x 相关文档不再出现 `list_skills`/`activate_skill`（那是 bm_recommend 的旧机制）。

## Part 6 · 优化方案（磁盘落地动作清单）

> 落地口径：改磁盘文件 + git 留档；不改 DB。每项标注"dev 生效前置"。

**A. SKILL.md 去重（改** `adswin_root_skill/SKILL.md`**）**

1. 删除「状态保存与状态机」整段（§353-371），替换为一行指针：`> 状态机与 state_save 契约见 system prompt「状态管理契约」，此处不重复。`（保留 0.0–7.0 各步骤内联的具体 `state_save(...)` 调用——那是流程细节，属 SKILL.md）。
2. 删除「禁止直接输出」(§373-375)，并入上面的指针（指向 Prompt「交互契约」）。
3. 删除「URL 传递原则」(§381-383)，替换为指针指向 CLAUDE.md §3；保留「素材附件提取原则/图片处理/辅助图片区分」等**流程操作细节**（这些是 SKILL.md 该拥有的层级）。

**B. 清除** `upsert_preview_feishu` **死引用（改** `adswin_root_skill/SKILL.md`**）** 4. 删除 §244 步骤 6.0-⑤ 及 §422 必用工具项。 5. **需先核对**：§238-242 的 `ad_preview` / `{value,enum}` 格式是否**仅**服务于已废弃的 upsert 路径；若 `render_ad_preview_table` 仍需要则保留、否则一并清理。核对点：`render_ad_preview_table` 的入参契约（`ads_agent/mcp_server.py` + `tools/`）。

**C. git 纳管建议（需用户拍板，Part 3 已说明利弊）** 6. 建议在 `.gitignore` 为 adswin_x 的 CC skills 增加白名单例外（如 `!data/claude/skills/adswin_x/`），让 SKILL.md 改动可 diff/review/留档，根治 P3。若维持现状，则每次磁盘改动都要额外记录，且 `56fdff2` 式丢失会复发。

**D. dev 生效前置（每次改完磁盘后，用户自理）** 7. 因 dev `prompt_source/skill_source=db`，磁盘改动需同步进 DB（`adk_prompts` / `adk_skills`）才在 dev 生效——本方案不执行此步，仅提示。改 Prompt 时按惯例 bump `audit_version`（当前 `v2026072301`）。

**本方案不改动**：Prompt 与 CLAUDE.md 内容（经 `56fdff2` 后已是三层的"权威所有者"，本轮只做 SKILL.md 侧的去重与指针化，使其向上对齐）。
